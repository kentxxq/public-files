# Git 提交与推送流程

当用户手动触发，禁止自动执行！用于将代码变更提交并推送到远端仓库。默认流程不涉及版本号；仅当用户主动要求发版时，才按第 2 章执行版本递增与发布（更新版本号、CHANGELOG/README）。

## 1. 梳理变更内容

在提交之前，需要确认本次修改的具体内容，以便编写准确的提交信息。

1. **查看状态**：
   - 运行 `git status` 查看已修改的文件。
   - **默认不处理版本号**：除非用户在本次请求中明确要求发版/更新版本号，否则不检查、不修改、不递增任何版本号。

2. **总结变更**：
   - 识别本次提交的核心目的（是新功能、修复、优化还是清理）。
   - 仅在用户主动要求发版时，才提取并确认新的版本号（如 `0.0.6`）。

## 2. 版本号与发布（可选，仅在用户主动要求时使用）

> **前置条件**：版本号与发布是**可选**流程，不属于默认提交步骤。只有用户主动提出「发版」「更新版本号」「递增版本」「release」等要求时，才按本章规则处理；其余情况下直接跳过本章，提交信息中不带版本号，也不打标签。

遵循语义化版本 `MAJOR.MINOR.PATCH`，按变更影响范围决定递增哪一位，一次发布只递增一个字段。

| 递增位 | 触发条件 | 常见场景 |
| --- | --- | --- |
| `MAJOR` | 不兼容的破坏性变更（**必须由用户显式指定**） | 删除/修改现有公开 API、行为不兼容、配置文件或数据格式不兼容、移除功能 |
| `MINOR` | 向后兼容的新功能 | 新增 API/页面/命令/配置项、新增可选参数 |
| `PATCH` | 向后兼容的修复与优化 | Bug 修复、性能优化、重构、依赖升级、样式调整、文档更新 |

**递增约定**：

1. 递增 `MAJOR` 时 `MINOR`、`PATCH` 归零（`1.4.2` → `2.0.0`）；递增 `MINOR` 时 `PATCH` 归零（`1.4.2` → `1.5.0`）；递增 `PATCH` 只加 `PATCH`（`1.4.2` → `1.4.3`）。
2. **`MAJOR` 完全由用户自己指定**：即使判断为破坏性变更，也**不得自行递增** `MAJOR`，只能提示用户「本次变更可能不兼容，是否需要递增大版本号？」，待用户明确确认后才递增；用户未确认时按 `MINOR` 或 `PATCH` 处理。
3. `0.x.y` 阶段（初始开发）可将不兼容变更体现为 `MINOR` 递增，不必等到 `1.0.0`，但需在提交信息中说明破坏性影响。
4. 版本号只增不减，禁止回退或复用已推送的版本标签；回滚变更应发布新的 `PATCH` 版本。
5. 递增后必须同步更新项目内所有版本号来源（如 `package.json`、`pyproject.toml`、`Cargo.toml`、README 徽章等），保持各处一致，并确保 Git 标签与版本号完全对应。
6. 用户未主动要求发版时，禁止擅自修改版本号或创建版本标签。

**发布操作步骤**（先检查是否有代码变更，如果没有变更，发布流程立即结束）：

1. **梳理变更范围**：查看上一个版本标签（`git tag --sort=-v:refname | head -n 1`）以来的 commit 记录，总结本次发布包含的所有变更；如无上一个标签，则汇总全部提交。
2. **确定新版本号**：按上表规则递增，得到 `X.Y.Z`。
3. **修改项目版本号**：更新项目中的版本号来源，例如前端项目修改 `package.json` 的 `"version"` 字段。
4. **更新变更日志**：
   - 检查是否存在 `CHANGELOG.md`；存在则写入 `CHANGELOG.md`，否则写入 `README.md`。
   - 在文件的二级标题「变更日志」下追加条目，每次发布以 `### vX.Y.Z (YYYY-MM-DD)` 格式开头，后接本次变更列表。
5. **后续动作**：如需提交与打标签，继续执行第 4 章；用户只要求更新版本与文档时，到本步为止。

**变更日志格式示例**：

```md
## 变更日志

### v1.2.3 (2024-01-01)

- 通过检查 `package.json` 中的版本号变更，自动化生成提交信息。
- 版本号变更时自动打标签并推送标签到远端。
- 通过使用 Emoji 增强提交信息的可读性。
```

## 3. 准备提交信息

使用 Emoji 增强提交信息的可读性。

- ✨ `feat`: 新功能
- 🐛 `fix`: 修复问题
- 🛠️ `refactor`: 代码重构/优化
- 📝 `docs`: 文档更新
- 💄 `style`: 样式调整
- 🗑️ `chore`: 琐事、清理或构建工具变更

**格式建议**：
提交信息永远使用中文描述，在必要的地方添加英文关键词。单词改动内容较多的时候可以有多行的提交信息，第一行是简短描述，后面可以有更详细的说明。

下面是第一行提交信息的格式建议：

- 普通提交（默认）：`:emoji: <类型>: <简短描述>`
- **带版本的提交**（仅在用户主动要求发版时）：`v<版本号> :emoji: <类型>: <简短描述>`

下面是一个普通提交信息示例（默认使用）
```md
✨ feat: 添加自动化发布功能

- 新增自动化发布脚本与相关配置。
- 提交信息使用 Emoji 增强可读性。
- 未涉及版本号变更与打标签。
```

下面是一个带版本号的提交信息示例（仅用户主动要求发版时使用）
```md
v0.0.6 ✨ feat: 添加自动化发布功能

- 通过检查 `package.json` 中的版本号变更，自动化生成提交信息。
- 版本号变更时自动打标签并推送标签到远端。
- 通过使用 Emoji 增强提交信息的可读性。
```


## 4. 执行提交、打标签与推送

1. **暂存文件 (Git Add)**：
   - 运行 `git add .` 暂存所有变更。

2. **提交变更 (Git Commit)**：
   - 运行 `git commit -m ":emoji: <message>"`。
   - 仅在用户主动要求发版时，提交信息才以 `vX.Y.Z` 开头。

3. **打标签 (Git Tag - 仅在用户主动要求发版时执行)**：
   - 默认不打标签；只有用户主动要求发版，且版本号已同步更新后，才为本次提交打上对应版本标签。
   - 若本次需要递增 `MAJOR`，必须先获得用户明确确认，未确认前不得递增或打大版本标签。
   - 运行 `git tag v<版本号>` (例如: `git tag v0.0.6`)。

4. **推送至远端 (Git Push)**：
   - 检查当前分支：`git branch --show-current`。
   - 运行 `git push origin <branch_name>`。
   - **推送标签**：仅在用户主动要求发版并打了标签时，运行 `git push origin --tags`。
