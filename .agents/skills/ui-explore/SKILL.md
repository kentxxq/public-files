# UI Explore

## 目标

针对现有页面或组件，设计并实现多个不同的 UI 方案，让用户在真实页面中直接切换、体验和选择。

重点改善布局、信息层级、操作流程和交互体验，而不是重新设计项目的视觉风格。

方案必须使用真实组件和业务逻辑实现，不使用静态设计图或 Mockup 代替代码。

## 基本原则

- **风格一致**：沿用项目现有组件库、主题、设计规范和样式体系。
- **实质性差异**：不同方案应体现布局或交互方式的差异，而不是简单修改颜色、间距或圆角。
- **共享逻辑**：复用现有状态、数据获取、事件处理和业务逻辑。
- **同文件优先**：优先在现有文件中实现多个方案，不强制拆分组件。
- **最小侵入**：尽量减少代码和文件变更，不引入不必要的抽象、依赖或架构变化。
- **快速探索**：优先提供可体验的候选方案，不在探索阶段投入大量测试成本。
- **保持行为**：不改变原有业务规则、数据语义和接口契约。
- **方便收敛**：用户选定方案后，能够轻松删除其他方案及临时代码。

## 1. 理解现有界面

修改前检查：

- 页面用途和主要用户操作流程。
- 当前布局、信息层级及存在的问题。
- 现有 UI 组件库、主题和样式约定。
- 当前状态管理、数据获取、事件处理和业务逻辑。
- 可以复用的现有组件与交互能力。

优先延续项目已有设计语言，不主动修改全局主题、字体、色彩体系或无关页面。

不为了 UI 探索而引入新的组件库或独立设计系统。

## 2. 设计多个方案

默认生成 3 个具有实质性差异的方案，用户指定数量时按要求执行。

每个方案都应有明确的设计思路，并针对实际问题进行改善。

重点探索：

- 页面布局与空间组织；
- 信息层级与内容展示方式；
- 导航与操作入口；
- 表单、列表、侧边栏、弹窗等交互方式；
- 信息密度与渐进式交互；
- 不同屏幕尺寸下的布局与操作体验。

方案之间应具有明显的交互或布局差异，不生成仅有细微视觉变化的重复方案。

不机械套用固定模板，应根据实际业务场景选择设计方向。

## 3. 多方案实现

### 同文件优先

优先直接在当前页面或组件中实现多个方案，减少文件与代码变更。

- 默认在同一个文件中，通过条件渲染或现有框架支持的方式切换方案。
- 共享现有状态、数据获取、事件处理和业务逻辑。
- 不为不同方案重复创建业务方法、接口调用或数据模型。
- 允许探索期间存在少量临时 UI 代码重复，不为了消除重复而提前抽象。
- 只有单文件明显难以维护，或确实存在独立组件职责时，才考虑拆分文件。

不同方案主要改变布局和交互结构，而不是复制整套功能实现。

### 真实交互

所有方案都应基于现有真实业务功能实现：

- 使用现有数据来源和接口。
- 保留原有核心操作能力。
- 按钮、表单、导航等交互应连接真实事件和业务逻辑。
- 保持现有加载、错误和业务状态的处理方式。
- 不使用假按钮、无效事件或伪造的业务结果。

如果原有功能尚未实现，应明确说明，不将其伪装为可用功能。

### 最小侵入

- 优先只修改当前页面或组件。
- 不修改无关业务逻辑、接口、数据库或数据模型。
- 不为 UI 探索创建永久性的抽象、状态管理或架构。
- 不主动重构无关代码。
- 不引入不必要的新依赖。

## 4. 页面内切换

在当前页面增加简单、明显的临时方案切换控件。

优先使用现有组件库提供的按钮组、标签页或其他合适的切换组件。

要求：

- 能够直接切换所有方案，不需要修改代码或刷新页面。
- 显示方案名称，方便识别和比较。
- 切换后立即展示对应方案。
- 不同方案共享必要的业务数据和状态。
- 避免切换造成重复请求、意外提交或数据丢失。
- 用户可以反复切换并体验不同交互方式。

如果切换方案会销毁和重建界面组件，应确保需要保留的数据和编辑状态不会意外丢失。

切换控件仅用于方案探索，不属于正式产品功能。

## 5. 方案验证

UI 探索以快速实现和比较不同方案为优先，不强制进行完整测试。

- 优先保持现有业务逻辑不变，仅修改布局和交互结构。
- 实现时检查明显的语法、类型和组件使用问题。
- 不主动启动开发服务器、浏览器或执行 E2E 测试。
- 不要求为每个候选方案生成截图、视频或测试报告。
- 由用户在现有开发环境中切换和体验不同方案。
- 只有用户明确要求验证，或发现影响基本功能的明显问题时，才进行必要的运行验证。

未实际运行时，不宣称方案已经通过运行验证。

## 6. 用户选择与最终收敛

完成多个方案后，保留方案切换能力，让用户自行体验和选择。

不要擅自认定最终方案。

用户明确选择后：

1. 保留选中的 UI 方案。
2. 删除其他方案和临时切换控件。
3. 清理探索期间产生的冗余代码、状态及样式。
4. 保留原有业务逻辑、接口和数据模型。
5. 根据实际改动范围验证关键行为。
6. 如果涉及业务规则、接口契约或架构变更，检查是否需要更新相关设计文档。

最终代码应恢复为正常的单方案实现，不保留无意义的探索分支。

## 约束

- 不擅自改变项目的整体视觉风格。
- 不随意替换或增加 UI 组件库。
- 不强制将不同方案拆分为多个组件文件。
- 不复制业务逻辑来实现不同方案。
- 不使用无法交互的静态页面代替真实实现。
- 不为了比较方案增加永久性的产品复杂度。
- 不修改无关页面或模块。
- 不为假想需求增加抽象。
- 不强制启动项目或执行完整测试。
- 不在用户选择前删除候选方案。

## 完成标准

完成 UI 探索时，应满足：

- 提供多个具有明显布局或交互差异的方案。
- 所有方案均基于真实组件和业务逻辑实现。
- 用户可以通过页面内控件直接切换和体验。
- 沿用现有组件库、主题和样式体系。
- 保持原有核心业务行为。
- 尽量减少代码和文件变更。
- 简要说明各方案的设计特点及尚未验证的部分。

完成探索后停止，保留候选方案供用户选择。只有用户明确选定方案后，才进行最终清理。
