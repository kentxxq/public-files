# Audit

## 目标

通过串联已有 Skill，检查 Design、Code、Tests 是否保持一致，识别真实缺陷、不必要的复杂度和有价值的改进机会。

Audit 负责组织审计流程、汇总证据、确定优先级和制定改进计划，不重复定义其他 Skill 的专业规则。

## 执行流程

### 1. 确定审计范围

- 用户指定范围时，严格限定在指定范围及必要的关联模块内。
- 未指定范围时，优先选择一个具有明确边界的子系统进行审计。
- 全项目审计应按子系统分批进行，不因一次检查而宣称整个项目已完成审计。
- 优先关注核心业务、近期修改、复杂模块和已有问题集中的区域。

### 2. 收集上下文

阅读相关的 `docs/design/`、实际代码和现有测试，理解模块职责、业务规则、数据流及关键约束。

- 优先阅读整体架构和当前审计范围对应的设计文档。
- 不无差别读取整个代码库和所有文档。
- 设计文档缺失时，不自动创建。
- 不因代码与设计不一致就直接认定代码或设计中的某一方错误。

### 3. 调用 Review

使用 `review` Skill 执行静态审查，重点检查：

- Design 与 Code 是否一致；
- 业务逻辑、模块职责、接口契约和不变量是否正确；
- 是否存在前后不一致的行为或遗漏；
- 是否存在冗余代码、过度抽象、不合理分支等质量问题；
- 是否存在明显性能问题和设计缺陷。

保留 Review 提供的问题证据，不重复实现其检查规则。

### 4. 调用 Test

使用 `test` Skill 检查现有测试的有效性，并实际执行适当的测试。

- 检查关键设计规则和公开行为是否得到验证。
- 根据需要执行 Unit、Integration 和 E2E。
- 记录通过、失败、跳过及无法执行的情况。
- 必要时保留人类可读的日志、测试报告、截图或视频。
- 识别重要的测试缺口，但不为了提高覆盖率而强行增加测试。

审计期间只执行检查和验证，不自动修改测试或降低断言标准。

### 5. 汇总问题

合并 Review 和 Test 的结果，去除重复问题，并区分：

- **设计偏差**：Code 不符合当前有效设计。
- **设计疑点**：设计本身可能存在冲突、过时或不合理之处。
- **实现缺陷**：代码存在逻辑错误或行为不一致。
- **测试缺口**：关键行为缺少有效验证。
- **代码质量问题**：存在不必要的复杂度、重复实现或过度设计。
- **性能问题**：存在有证据支持的性能缺陷或值得验证的潜在瓶颈。

区分已确认问题、待验证问题和改进建议。没有证据的问题不得作为确定缺陷报告。

### 6. 调用 Refactor Plan

针对已确认且值得处理的问题，使用 `refactor` Skill 的 `plan` 模式制定改进方案。

- 优先删除冗余代码、合并重复实现、降低嵌套和简化职责。
- 评估改动范围、潜在风险和预期收益。
- 明确需要执行哪些测试来验证重构结果。
- 性能优化必须有实际证据支持。
- 不为每个发现的问题强行制定重构方案。
- 不重复实现 Refactor 的重构分析规则。

如果问题涉及业务规则或设计契约变更，应先明确需要确认的设计决策，不得直接将行为变更混入重构计划。

## 审计约束

- Audit 默认只读，不修改代码、测试或设计文档。
- 不自动执行 Refactor 的 `apply` 模式。
- 不重复维护 Review、Test 和 Refactor 已定义的规则。
- 不因测试缺失就认定代码无用，也不因测试通过就认定设计正确。
- 不为假想需求增加复杂度，不为了发现问题而强行提出改进。
- 不将无法执行的测试描述为已通过。
- 不因局部代码问题自动扩大审计范围。
- 当设计与实现的正确方向无法确定时，明确列出冲突及需要人工决定的事项。

只有用户明确要求进入修复阶段时，才继续执行重构；修复应作为独立阶段进行，并重新验证。

## 输出格式

生成简洁、可追溯的 Markdown 审计报告。

### 1. 审计范围

记录本次检查的子系统、主要文件、设计文档和执行过的测试。

### 2. 审计结果

列出确认的问题，每项包含：

- **问题**：具体描述。
- **证据**：对应设计、代码位置或测试结果。
- **影响**：正确性、维护成本或性能风险。
- **优先级**：P0 / P1 / P2。
- **建议方向**：简要说明处理思路。

优先级定义沿用 Review Skill，不重复制定新的分级规则。

### 3. 验证结果

记录实际执行的测试、通过与失败情况，以及未执行或无法验证的内容。

### 4. 重构计划

按优先级列出值得执行的改进项，说明：

- 预期修改；
- 影响范围；
- 行为保持要求；
- 验证方式。

### 5. 待决事项

列出需要用户确认的设计冲突、行为变更或无法确定的问题。

没有发现值得处理的问题时，明确报告结果，不为了输出完整报告而虚构问题。

## 完成条件

- 已完成所声明范围内的审查。
- 已记录实际执行的测试和验证结果。
- 重要问题具有明确证据。
- 重复问题已经合并。
- 有价值的改进已有相应的重构计划。
- 未解决的问题和未检查的范围已明确说明。

达到以上条件后停止，不自动扩大审计范围或继续重构。
